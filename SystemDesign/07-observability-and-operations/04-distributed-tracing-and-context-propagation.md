# Distributed Tracing and Context Propagation

> **TL;DR:** A distributed trace is a tree of timed "spans" showing exactly how one request's time was spent across every service, thread, and network hop it touched. It only works if a trace context (trace_id + parent span_id) is propagated through every hop — in HTTP headers, message queue metadata, everywhere — which is the part most implementations get wrong.

## Quick Reference

| Concept | Definition |
|---|---|
| Trace | The full tree of spans for one logical request/transaction |
| Span | One timed unit of work (a function call, an RPC, a DB query) with start/end time, name, attributes |
| Trace ID | Globally unique ID shared by every span in a trace |
| Span ID | Unique ID for one span; child spans reference parent's span ID |
| Context propagation | Passing trace_id/span_id across process boundaries (HTTP headers, queue message metadata) |
| Standard header | W3C Trace Context: `traceparent: 00-{trace_id}-{span_id}-{flags}` |
| Sampling | Deciding which traces to keep (head-based at start, tail-based after seeing outcome) |
| Standard/SDK | OpenTelemetry (OTel) — vendor-neutral instrumentation, replaced OpenTracing + OpenCensus |

## What It Is

- A **span** captures one unit of work: name, start/end timestamps, status, key-value attributes (`http.method`, `db.statement`), and a reference to its parent span.
- A **trace** is the causal tree formed when spans reference each other across a request's full path — client → gateway → service A → service B → DB, each hop a span, nested under the one that called it.
- Distinguishes itself from logging/metrics by capturing **causality and timing structure** across process/network boundaries, not just isolated facts or aggregates.

## Responsibilities

- Every service in the call path must: extract incoming trace context from the request, create a child span, do its work, and inject the (possibly updated) context into any outbound calls it makes.
- The tracing SDK must add negligible overhead (microseconds per span) since it runs on every request in the hot path.
- The collector/backend must reconstruct the full trace from spans that may arrive out of order, from different hosts, and assemble them into a coherent waterfall view.

## How It Works

```
Client
  │  (no incoming trace context — this service starts the trace)
  ▼
API Gateway         span: trace_id=T1, span_id=S1, parent=none
  │  injects traceparent header into downstream call
  ▼
Checkout Service     span: trace_id=T1, span_id=S2, parent=S1
  │  injects header
  ├──▶ Inventory Service   span: trace_id=T1, span_id=S3, parent=S2
  └──▶ Payment Service     span: trace_id=T1, span_id=S4, parent=S2
                               │
                               ▼
                          DB call            span: trace_id=T1, span_id=S5, parent=S4
```

- **Context propagation is the make-or-break mechanic**: if Checkout Service calls Payment Service without forwarding the `traceparent` header, Payment Service starts a *new* trace — the two are now disconnected, and the waterfall view breaks at that boundary. This is the most common tracing bug in real systems (a raw HTTP client used somewhere that bypasses the instrumented client wrapper).
- Propagation must also cross **async boundaries**: message queues (Kafka, SQS) need trace context embedded in message headers/metadata, not just HTTP headers, or async processing becomes an untraceable gap.
- **Sampling decision**: head-based sampling decides at the root span (e.g., "trace 1% of requests") — cheap but may miss rare slow/error requests. Tail-based sampling buffers all spans for a trace and decides after seeing the full outcome (e.g., "keep it if it errored or was slow") — better signal, but requires buffering and more collector infrastructure.

## Types / Classifications

| Type | Scope | Example tool |
|---|---|---|
| Distributed trace | Cross-service, cross-network | Jaeger, Zipkin, Tempo, X-Ray |
| In-process/profiling trace | Function-level within one process | pprof, async-profiler, language-native profilers |
| Synthetic trace | Generated by a scripted probe, not real user traffic | Synthetic monitoring tools (file 09) |
| RUM (Real User Monitoring) trace | Starts in the browser/mobile client, extends into backend | Datadog RUM, New Relic Browser |

## Where It Fits

- Complements logs and metrics as the third pillar (file 01) — traces are what you pivot to *from* a metric alert to find *where* the time went, then pivot *from* the trace to logs for *why*.
- Sits inside the service mesh/sidecar layer when auto-instrumented (Istio/Envoy can generate spans for every proxied call with zero app code changes, though app-internal spans still need SDK instrumentation).
- Feeds **APM** tooling (file 08) — APM products are largely built on top of trace data plus code-level profiling.
- Essential for debugging issues from **circuit breakers, retries, timeouts** (Section 06) — a trace makes visible exactly where a retry storm or cascading timeout actually originated.

## Pros & Cons / Trade-offs

| Aspect | Pros | Cons |
|---|---|---|
| Full (100%) tracing | Complete visibility, no blind spots | Storage/processing cost scales with total traffic — often prohibitive at scale |
| Head-based sampling | Cheap, simple, decided upfront | May systematically miss rare error/slow traces that matter most |
| Tail-based sampling | Captures the interesting cases (errors, slow) with much lower overall volume | Requires buffering all spans until the trace completes — more collector memory/complexity |
| Auto-instrumentation (mesh/agent) | Zero app code changes, consistent coverage | Only sees network-level spans — misses in-process detail (which DB query, which function) |
| Manual/SDK instrumentation | Rich, precise, code-level spans | Developer effort per service; easy to have gaps where someone forgot to instrument a call |

## Real-World Scenarios

- **Uber's original Jaeger use case**: hundreds of microservices meant a single user request could span 20+ services — without tracing, "why is this checkout slow" required manually correlating logs across 20 teams; tracing turned it into one waterfall view.
- **Broken trace at a queue boundary**: a service publishes to Kafka without forwarding trace context in message headers; the downstream consumer starts a fresh trace — on-call sees two disconnected traces and initially thinks it's two separate incidents.
- **Tail-based sampling at Google/Facebook scale**: with billions of requests/day, sampling 100% is impossible — tail-based sampling collects all spans in memory per trace for a short window and only persists traces that errored or exceeded a latency threshold, keeping <1% overall while catching nearly 100% of "interesting" traces.
- **Service mesh auto-tracing**: an Istio-based platform gets basic cross-service latency traces automatically via Envoy sidecars, with zero app instrumentation — good enough to identify *which* service is slow, but engineers still add manual spans inside that service to find *which function/query*.

## Nuances & Gotchas

- **A broken propagation link silently degrades to "two traces," not an error** — nothing crashes, you just lose the connection; this makes it easy to ship for months before anyone notices tracing has a gap at a specific hop.
- **Raw/unwrapped HTTP clients bypass instrumentation**: if a library auto-instruments the standard HTTP client but a service uses a raw socket or an unsupported client library, that hop won't propagate context — audit for this explicitly, don't assume "we use OTel" means every call is covered.
- **Async/queue-based systems need explicit propagation support**: OTel has semantic conventions for messaging systems, but many message queue client libraries don't propagate trace context by default — this must be added manually in the producer/consumer code.
- **Clock skew between hosts breaks waterfall visualization**: if host clocks aren't NTP-synced, child spans can appear to start before their parent — always ensure NTP/chrony discipline on all instrumented hosts.
- **High-cardinality span attributes are fine (unlike metrics)**: you can safely put a full user ID or raw SQL query on a span attribute — traces don't have the cardinality cost model that metrics do, since each trace is stored and queried individually, not aggregated into a time series.
- **Sampling rate tuning is a moving target**: a fixed 1% sample rate on low-traffic services might capture zero errors for days; adaptive/tail-based sampling avoids this but adds infra — teams often start with head-based and migrate to tail-based once trace volume/cost becomes the pain point.
- **Tracing overhead compounds in hot paths**: even microsecond-level span creation overhead matters at very high QPS services — batch span export (not synchronous per-span network calls) is essential, and most SDKs do this by default, but misconfigured "flush every span" setups have caused real production latency regressions.
